# MediFlow HMS – project brief

Software Engineering **Assignment 1 (Hospital Management System), Group 11**. A full-stack web HMS (patients, doctors, appointments, smart queue, consultation, lab, pharmacy, beds/admissions, billing, reports, audit) plus the assignment report (SRS, SDD with UML, Test Plan, Test Report).

Read `PROGRESS.md` (newest entry first) before doing anything. `README.md` has the user-facing run instructions and demo accounts; `DEMO.md` is the 10-minute demo script.

## Status
Feature-complete and ready to submit. The five submission documents (SRS, SDD, UML diagrams, Test Plan, Test Report) and the combined report are in `deliverables/`. Live demo at https://mediflow-hms-6vw1.onrender.com (Render). Remaining work is only fixes the group asks for.

## Environment and commands
- Node 20+ (via nvm). SQLite is embedded (better-sqlite3), no DB server.
- `npm install` once, then `npm run seed` and `npm run dev` → http://localhost:5173 (API on :4000).
- Tests: `npm test`, `npm run test:coverage`, `npm run test:e2e` (needs `npx playwright install chromium`).
- Report: run `npm run test:coverage` **before** `npm run test:e2e` (Vitest clears `docs/test-results/actuals.jsonl`), then `npm run report`. It needs LibreOffice for the PDF and table of contents (`brew install --cask libreoffice`; it was uninstalled after the 22 Oct 2026 build, so reinstall it first). Copy the outputs from `docs/report/build/` into `deliverables/`.
- Demo accounts: see README; all share the password `Mediflow@123` (seed data only).

## Deployment
- Render free web service from `render.yaml` (Blueprint, region Singapore, Node 22, `JWT_SECRET` generated by Render, health check `/api/health`). Auto-deploys on every push to `main`.
- Ephemeral disk: the SQLite DB is recreated and re-seeded on each deploy, restart and wake from idle sleep (15 min). Fine for a demo; persistence would need a paid disk.
- Live URL: https://mediflow-hms-6vw1.onrender.com (service `mediflow-hms`, Blueprint `mediflow-hms`). The URL is also set in `docs/report/data.mjs` (`LIVE_URL`), README and DEMO.md.
- The Render account and the GitHub access grant belong to the user; never sign in there for them.
- Vercel was rejected because serverless instances each get their own `/tmp` SQLite copy, so data would be inconsistent between requests.

## Project rules
- **Separate documents:** content functions use `PartH1()` and document names ("the Software Test Report", "SRS, Section 7"), never "Part A/B/C/D", so the same text works in the combined report and the standalone files. Each document's cover and Group Details page must show the group number, assignment number and title, and every member's name and registration number.
- **Report house style:** the report text must contain no em dash, en dash, semicolon or colon. `clean()` in `docs/report/lib.mjs` converts generated text (times 09.30, ranges "A to B", "Label. Text", lists in brackets) and `check_text.py` fails `npm run report` if any remain. Write new report prose without them.
- **No tool attribution anywhere in the repo:** commit messages have no co-author or session trailers, and files never name the coding assistant used. Any assistant-specific instruction file stays local only (list it in `.git/info/exclude`, never in `.gitignore`).
- Requirement, defect and test IDs must stay consistent across `docs/spec/*.json`, tests and the report; a defect's test ID must exist in the tests.
- Demo data is dated relative to seed time; reseed on demo day.
- `chat_history/` is local only (git-ignored).
